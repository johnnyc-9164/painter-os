# Bounded final security review

Source review only, approximately three minutes. No application files modified, no live deployment exercised, and no test-suite rerun. Existing test totals are reported by the implementation, not independently reproduced here. This is not production security certification.

## Confirmed findings / prioritized fixes

1. **High — command responses bypass role-based financial redaction.** `packages/domain/src/engine.ts: visibleEntities` removes `financialSnapshot`, `totalCents`, `depositCents`, `collectedCents`, and `billedCents` from jobs for crew roles. However, `applyCommand` returns raw `entity`/`entities`; `field.start` and `field.submit` include a touched job with those fields. `local-runtime.ts: commandLocal` returns this result unchanged; `convex/painter.ts: command` only sanitizes customer results. An authenticated crew member can receive financial data excluded from their snapshot via a permitted field command. **Fix:** apply the same actor-specific entity projection to every command result, including replay receipts, in both hosts. Add crew command/replay response tests asserting those job fields are absent.

2. **High — staff can approve on behalf of a customer through the generic command API.** `engine.ts: canCommand` grants owner/office_admin/estimator every estimate verb, including `estimate.approve`, `estimate.reject`, and `estimate.requestChanges`. The customer boundary check only runs when the actor already has role `customer`. Thus an estimator can approve a sent estimate directly through `/api/command` or the Convex mutation, recording an approval/approved financial snapshot without customer action. `docs/ir/permissions.yaml` lists `estimate.approve.customer` for customer only; the UI also directs approval to the secure portal. **Fix:** explicitly restrict customer-decision verbs to customer actors (or implement a separately named, explicitly audited administrative override if product policy authorizes it); test direct staff API denials, not only UI button absence.

3. **Medium — local bearer portal exposes draft invoice summaries.** `local-runtime.ts: portalLocal` returns all invoices linked to the estimate's jobs/customer without excluding drafts. The cloud `portalView` excludes `status==='draft'`, and deployment documentation promises non-draft summaries only. A previously issued proposal bearer can see unissued billing totals/balances in local acceptance mode. **Fix:** apply identical invoice publication filtering in both runtimes and test draft exclusion. Authenticated customer snapshots also currently include drafts through `visibleEntities`; specify publication policy and enforce it there if drafts must remain private.

4. **Medium — cloud workspace selection is inconsistent across reads/writes.** `convex-runtime.ts: snapshotCloud` accepts `workspaceId` for the snapshot but fetches the member roster without that ID. `commandCloud` and file/member adapters likewise do not propagate selected workspace IDs, while backend `resolve` defaults to the first enabled membership. A multi-workspace user can view workspace B while operations/roster target workspace A. This does not bypass membership checks, but can misdirect authorized writes and present a roster from the wrong workspace. **Fix:** propagate a validated selected workspace to all operations, including members, invitations, portals, and uploads; add a two-membership end-to-end test.

## Production blockers / known incomplete scope

- **No real Convex deployment or cloud session round-trip evidence.** The installed Next Better Auth bridge obtains request cookies via `next/headers`; the JSON adapter forwards Better Auth Set-Cookie and the UI subsequently refreshes the snapshot. No confirmed source-level cookie incompatibility was found in this bounded review. Provision the actual deployment and verify signup → cookies → authenticated snapshot/command → logout, mounted core component operations, and storage uploads before release. Mocked authenticated-user tests do not establish these properties.
- **Invitation onboarding cannot complete for ordinary new email/password users:** `auth.ts` has no verification-email callback/provider, while `acceptInvite` correctly requires `user.emailVerified`. Configure a real verification flow and test it; do not weaken the verified-email gate. Reset-email delivery is also absent.
- **Cloud issued links lack request-key semantics:** `commandCloud` intercepts portal/invite creation but does not send `requestKey` or portal `expectedRevision`; backend createPortal/createInvite have no receipt handling. Retrying can create additional valid bearer links. Add actor/tenant-bound idempotency and revision checking for these issuance operations.
- **Explicit unavailable functionality, not evidence of a full production product:** integration records are metadata only (`connected:false`); payments are manual receipt recording, not charging; subscription billing is unavailable; automation only performs bounded internal task/review creation, with no external sends/LLM chatbot; email/SMS/calendar/accounting adapters and delivery are not connected. The original core remains a separate store, not a mirrored product source of truth. Preserve these disclosures in acceptance/release claims.
- Portal revocation and cloud application-command rate limiting are not configured. Add revocation and abuse controls before exposing production bearer issuance publicly.

## Positive checks observed

Tenant/entity lookups are scoped to resolved membership or bearer-bound tenant; authoritative customer email binds portal decisions; immutable portal revision checking and transactional command receipts exist; money calculations use bounded minor units and reject overpayment; local mode requires explicit `PAINTER_RUNTIME=local` and does not silently replace failing cloud operations. These observations do not establish exhaustive absence of other vulnerabilities.
