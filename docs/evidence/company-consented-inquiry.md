# Consented public company inquiry — issue 150

This slice installs an optional contact request after the existing project guide. It uses the canonical publicLead mutation, receipt query and contactIntakeConfig public policy. Both existing server policies must be enabled and the guidance revision must match before the form appears. Current server-side owner/office-admin opt-in remains authoritative; this slice does not install its missing admin control or enable any company.

The public-content wrapper exposes three fixed anonymous capabilities. Company code imports no private runtime, session, aggregate snapshot or arbitrary dispatcher. Its policy/proof decoder strips no secret by guesswork: it rejects unknown fields. Submission normalization reuses the canonical pure backend contract; backend authentication, persistence and validators do not enter the public boundary. The .mjs namespace compatibility handles the repository's existing CommonJS TS loader for that pure contract, without duplicating its validation rules. No dependencies changed.

A same-origin POST-only route binds the workspace from its path. It closes action/body fields, accepts application/json only, consumes at most 16 KiB of actual streamed bytes, and cancels/rejects bodies after five seconds even if they already contain a valid JSON prefix. Browser and backend transport have bounded abort deadlines. Convex logger is disabled; route failures are constant codes, with no input or provider diagnostics echoed or logged. Request contact details, nonce and receipt are never query parameters, localStorage, sessionStorage or analytics. The backend owns retention and idempotent admission; memory state is not a replacement for its durable receipt.

Consent starts unchecked. Contact name and email and/or phone are collected separately from project guidance. The company policy and 30-day disclosure precede submission. A request freezes its normalized exact contact/project payload, key and policy revisions in memory. Network errors, malformed responses and unsuccessful HTTP responses remain unknown. Status unavailable allows only checking again or replaying the same original request; it does not authorize minting another key while the first request may arrive. A known policy denial unchecks consent and directs the visitor to reload/review, without automatic new intent. The questionnaire is keyed by workspace so client navigation cannot submit a previous company's contact or nonce into another workspace. Unknown intent is deliberately not keyed by policy revision and cannot be discarded by editing the project guide.

Received means recorded for review, not notified, accepted project, appointment, calendar booking, confirmation email or provider delivery. No provider, model, chat, calendar, outbound email, credentials, account registration, schema, private writer or production activation is included. Reload/navigation clears local pending state; visitors are instructed to reconcile uncertainty before leaving. This cannot prevent a visitor independently navigating away or opening another browser; durable backend same-key receipts govern only retained keys.
