# Company website publishing and media preparation

Scope: issue #126, canonical company-authored content, dedicated draft/published aggregate, owned website raster media. The authenticated dashboard remains the authoring authority; article publishing and private job-file upload writers are unchanged. Shared content lives in `packages/domain/src/company-website.ts` and is consumed by template/editor tracks. Templates are studio, editorial, and direct. Missing content produces no invented reviews, photos, prices, logo or business claims. Testimonials are manually authored; optional ratings are not verification or structured aggregate-rating evidence.

Owner/office-admin operations resolve an actual Better Auth user and the current enabled workspace membership. Writes require expectedRevision and actor-bound hashed idempotency receipts. Saving a draft preserves the prior published snapshot; publishing verifies every referenced ready media record belongs to the current company; unpublishing removes public projection. Content is bounded to 128 KiB, at most 50 media references, and capped section lists. Currency formatting uses a declared USD/CAD/GBP/EUR/AUD/NZD catalog. Audits contain revision metadata, not copies of content or contact fields.

Only authenticated server actions accept bounded binary bytes (at most 3 MiB). They reserve a durable company/actor/nonce receipt before storage effects and create a fresh blob using storage.store. No browser upload URL, storageId adoption, job-file reuse, public draft endpoint, external image URL or public mutation exists. Same-key duplicate requests replay or retain the existing operation; no second storage writer is admitted. Tenant admission is conservatively capped at 200 retained operations and three active unresolved operations. Ready library reads paginate at 50 records. This preparation has no media removal/editor-library lifecycle beyond failed upload cleanup; capacity exhaustion requires a later audited management operation.

The image-size 2.0.2 parser checks actual raster type and dimensions; structural bounds reject truncated PNG/JPEG/WebP, SVG and animated WebP. Maximum dimensions are 10,000 per axis and 40 million pixels. This is header/structure validation, **not full pixel decoding or proof that a raster is completely renderable**. No EXIF stripping or image transformation occurs. Uploaded content may retain embedded metadata; editors must choose appropriate public material.

Staging registers the server-created storage ID in a quarantined receipt, then finalization rechecks current membership and actor. Known staged failure/revocation enters cleanup_pending and deletes the owned blob before marking deleted. A ten-minute scheduled reconciliation handles abandoned reservations. The ready state cannot enter quarantine cleanup. Unknown storage RPC outcomes, or interruption after storage succeeds before the returned ID is registered, retain reconciliation_required; the nonce cannot be reused for a new store. An inaccessible storage ID cannot be located or physically removed by this receipt: this implementation does **not** claim complete orphan reconciliation or deletion. A failed cleanup stays pending and the internal reconciliation action can safely retry the owned deletion; there is no public cleanup action or blind upload retry.

Public image GET /company-website-media requires exactly workspaceId/mediaId/revision and resolves the current published snapshot association before and after storage retrieval. Old publication revisions, unpublishing, unknown companies and foreign/unreferenced media return unavailable. Responses are no-store/nosniff raster bytes, never storage download URLs. Public snapshots use only the fixed origin-relative /api/company-website-media proxy URL. Authorized private preview/read uses /api/website/media, current membership and optional exact saved draft revision. The action rechecks authority after fetching bytes. Responses already in flight cannot be recalled after unpublish/revocation; no cache is authorized.

Transport verification uses installed convexToJson/jsonToConvex serialization and a local Convex action at exactly 3 MiB and one byte above. The serialized boundary is below 5 MiB. Official Convex limits documentation states 16 MiB function arguments and 5 MiB for Node actions; this action uses the default runtime. Local fixtures are not production deployment/upload/limit acceptance. The editor must separately enforce multipart overhead, actual file size and its deployment request body limit.

Local checks and independent review/CI receipts are recorded on the implementation PR. Fixtures include actual Better Auth component sessions and revoked roles, immutable publication, stale revisions, private/raw storage rejection, fresh storage provenance, tenant separation, concurrent null-status retries yielding one receipt/blob, declared byte limits, supported raster truncation and known staged cleanup. No source company data, cloud resource, live upload, provider activation or domain cutover is performed.

Skill extraction: reused `docs/skills/painter-pr-evidence/SKILL.md`; no new procedure created. Runtime/source proof remains separate from cloud acceptance, and broad website/release issues remain open until editor/template integration and deployment gates are verified.
